# TERANGA-05A — Conversion, attribution and measurement architecture

Audience: engineers maintaining the site, and the owner when deciding the release gates. Baseline: `docs/TERANGA-05A-baseline-audit.md`. Event names: `docs/TERANGA-05A-analytics-taxonomy.md`. Operations: `docs/TERANGA-05A-lead-operations.md`. Privacy and security: `docs/TERANGA-05A-privacy-security.md`.

No framework, database, dependency or third-party tracker was added. The site is still static HTML generated by `site/build.mjs`, with one Vercel function (`api/contact.js`) and Resend for notifications.

## 1. Flow

```
Visitor's browser (main.js)                         Vercel function /api/contact            Owner
───────────────────────────                         ─────────────────────────────           ─────
landing page ── reads utm_* tags, referrer host, ─┐
                entry path → sessionStorage tt-src │
CTA "Discuss your …" → /contact?service=ai         │
form: validate → POST {fields, lang, page, source} ┼─► size ≤ 32 KB, rate limit (5 / 10 min / IP)
                                                   │   validate fields; clean attribution
                                                   │   (allow-list, bounds, host only, path only)
                                                   │   channel = campaign | referral | direct
                                                   │   Resend: notification (+ attribution,
                                                   │   tracker row, tag channel), idempotent,
                                                   │   4 s × 2 attempts                      ─► inbox (Gmail)
◄── 200 {message, ref}  (only if Resend accepted) ─┘                                             │
confirmation "Thank you…" + reference                                                            ▼
events → window.TT.events / tt:analytics                                     paste tracker row into private sheet
(→ Vercel only when custom events are enabled)                               export CSV → scripts/lead-report.mjs
page views → /_vercel/insights (when enabled)
```

## 2. Conversion experience

| Element | Implementation |
|---|---|
| Standard CTA | `common.cta` = "Discuss your project" / "Parlons de votre projet" (header, mobile menu, closing band). Service and case-study CTAs keep the same verb: "Discuss your SaaS project", "Parlons de votre projet IA", etc. A test pins the wording |
| Service-aware CTAs | `button({ service })` links to `/contact?service=<key>` and adds `data-service`; `main.js` preselects the option when the key exists. 9 such CTAs per language (6 on Services, 2 on Work, 1 on AI Engineering) |
| Form | Unchanged fields and API contract. Changes: the "started" signal is now the first input rather than focus; the privacy note links to the privacy page |
| Confirmation | `#f-confirm` panel (rendered hidden). Shown only when the response is 2xx, i.e. after Resend accepted the notification. Text EN: "Thank you. Your project inquiry has been received. We aim to respond within one business day." FR: "Merci. Nous avons bien reçu votre demande. Nous nous efforçons de vous répondre sous un jour ouvré." It shows the reference from the response (format checked, `TT-YYYYMMDD-XXXX`; the box is hidden if absent). Focus moves to the panel heading; "Send another request" restores the empty form and focuses the name field |
| Failure | Unchanged: an honest error with email and WhatsApp links pre-filled with the visitor's request; the input is kept |
| Booking | No booking claim anywhere: the confirmation says the request was received, not that a call is booked (`BOOKING_URL` stays empty) |
| Budget field | Not added: currency and ranges are still an owner decision (baseline §7.9) |
| Privacy page | `/privacy` and `/fr/privacy`, linked from every footer and from the form. The analytics section is rendered only while the analytics script is on |

The lead reference format did not change. The success response now includes it: `{ "message": "Request sent.", "ref": "TT-20261023-3F9A" }`. A duplicate submission within 10 minutes on the same instance returns `{ "message": "Request already received.", "ref": <first reference> }`, so the visitor always sees the reference of the notification that was actually sent.

## 3. Attribution

### Capture (browser, `visitSource()` in `main.js`)

| Rule | Behaviour |
|---|---|
| What | `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` (each cut to 150 characters), the referring site's **host name only** (`new URL(document.referrer).hostname`; never its path or query), the entry path |
| When | On every page load. A page with campaign tags or an external referrer starts a new attribution (entry = that page). Otherwise the saved one is kept |
| Language redirects | Read before the `/` → `/fr` and legacy-hash redirects. The redirect sets `tt-hop`, and the next page keeps the saved attribution and updates the entry page to the page actually shown. Otherwise the redirect would replace the real referrer with the site itself |
| Storage | `sessionStorage` `tt-src` (and the one-shot `tt-hop`): first-party, cleared when the tab closes, no identifier, never a cookie |
| Sent | Only inside a form submission, as `source`, with `page` = the conversion path |

### Validation (server, `cleanAttribution()` in `api/_lib/contact.js`)

All attribution is untrusted input:

| Field | Rule |
|---|---|
| `utm_source`, `utm_medium` | String only, one line, `< > " ' \` \\` removed, whitespace collapsed, 100 characters |
| `utm_campaign`, `utm_content`, `utm_term` | Same, 150 characters |
| `referrer` | Host name extracted from a bare host or URL, validated label by label (letters, digits, hyphen; TLD alphabetic or `xn--`), ≤ 253 characters; the site's own domain is dropped |
| `entry`, `page` | Path only (query and fragment removed), lower-case, `^/[a-z0-9/-]{0,79}$`, no `//` |
| Anything else | Ignored (for example a `channel`, `email` or `name` key in `source`) |
| `channel` | Computed on the server: `campaign` if any UTM tag, else `referral` if a referrer, else `direct` |

### Output

- **Notification:** an "Attribution (as reported by the visitor's browser)" section (channel, source, medium, campaign, content, term, referrer, entry page, conversion page; absent fields left out). HTML-escaped in the HTML part.
- **Tracker row:** a tab-separated line in the documented column order. Its Source column holds the `utm_source` tag or, for referrals, the referrer host. Cells starting with `= + - @` are prefixed with `'` so a pasted cell can never run as a spreadsheet formula. The row has no name, email or message.
- **Resend tag:** `channel` (with `inquiry_type`, `service`, `lang`), for filtering in the Resend dashboard.
- **Log line:** `channel` instead of the previous `sourced` flag. Still no personal data.

## 4. Measurement

| Piece | Implementation |
|---|---|
| Switches | `ANALYTICS` in `site/config.mjs`: `webAnalytics` (script on every page), `customEvents` (forward events to Vercel), `maxEventProperties` |
| Page views | `<script defer src="/_vercel/insights/script.js">` in `<head>` (same origin, allowed by the CSP `script-src 'self'`; beacons go to `/_vercel/insights/*`, allowed by `connect-src 'self'`) |
| Events | `emit()` in `main.js`: validates against `EVENTS`, deduplicates, appends to `window.TT.events` (last 50), dispatches `tt:analytics`, and only when `<body data-va-events="N">` is present queues `va('event', {name, data})` with the first N properties |
| Queue | When forwarding is on, `main.js` defines the standard `window.va` queue. `main.js` runs before the deferred Vercel script, which replays the queue |
| Server records | The tracker, fed from notifications. No server-side event store was created: nothing new needs protecting, and nothing private is published |

**Activation (updated 2026-10-23, `docs/TERANGA-05A-analytics-activation.md`):**
- Web Analytics was enabled for the project at 19:33 UTC.
- Vercel adds the `/_vercel/insights/*` routes only to deployments **created after** that. An older deployment answers 404 for the script, logs one console error per page view and records nothing.
- After enabling (or re-enabling) Web Analytics, redeploy, then run `node scripts/check-analytics.mjs <url>`. No code change is needed.
- The team is on **Pro**: custom events are available (2 properties per event, 8 with Web Analytics Plus), and page views and events are billed as usage.
- The Vercel script ignores automated browsers (`navigator.webdriver`, "Headless" user agents), so automated tests never add page views.

## 5. Notification delivery semantics (unchanged contract, now documented)

| Server outcome | HTTP | Visitor sees | Event | Lead? |
|---|---|---|---|---|
| Resend accepted (first or second attempt, same idempotency key) | 200 + `ref` | Confirmation with reference | `lead_submit_success` | Yes: notification on its way. "Accepted" is not proof of inbox delivery; Resend "Delivered" plus the message in Gmail is |
| Same request within 10 min on the same instance, first one accepted | 200 + first `ref` | Same confirmation | Not counted again (same reference) | No new lead |
| Same request while the first is still sending | Waits for the first, then the same answer | Same as the first | — | No new lead |
| Resend refused (bad key, unverified domain, quota) | 502 | Error + pre-filled email/WhatsApp | `lead_submit_failure` `server` | No: not recorded anywhere; the visitor is asked to use email/WhatsApp. Visible in Vercel logs (`Lead email failed`) |
| Resend timed out twice (4 s each) | 502 | Same | `server` | No (Resend may still deliver late: the idempotency key prevents a duplicate on retry) |
| Resend not configured | 503 | Same | `server` | No (`Lead email not configured: missing …` in logs) |
| Invalid input (since TERANGA-05C: the answer names the field) | 400 `{message, field}` | That field marked with its message and focused; "check the highlighted field" | `rejected` | No (log `Lead rejected` with the check that failed, never the values) |
| Honeypot filled | 400 `{message}` (no field) | Generic error + pre-filled email/WhatsApp | `rejected` | No (log `Lead rejected` `honeypot`) |
| Too large (> 32 KB) | 413 | Generic error | `rejected` | No |
| Rate limited (6th request in 10 min from one IP on one instance) | 429 | Generic error | `rate_limited` | No |

There is one delivery mechanism (Resend). If it fails, the server never reports success.

## 7. Performance

The baseline measured a 139–213 ms `main.js` task on the home page under mobile throttling, almost all of it style and layout (scripting itself is 15–50 ms). `initReveal()` read element positions with `getBoundingClientRect()` while the script ran, which forced the page's first layout (and, before this release, one more per element) into the script's task. A first fix that only batched the reads did not shorten the task: the first layout was still forced. It now reads no layout at all. A first IntersectionObserver report sorts the elements after the browser's own layout: those on screen or above it stay as they are, and those below get `reveal-pending`. Opacity and transform only, so no layout shift. A second observer reveals them on scroll. Figures: release report.

## 8. Known limits

- Rate limit and duplicate guard are per serverless instance (best effort). For a global limit add a Vercel Firewall rule on `POST /api/contact` (owner, dashboard).
- Attribution is self-reported by the browser: it can be forged or missing (privacy tools strip referrers; ad blockers block analytics). It is bounded and labelled as such in the notification, and is good enough for channel-level decisions.
- Attribution lives in the tab's session: a visitor who comes back later in a new tab is "direct".
- Page views are recorded only by deployments created after Web Analytics was enabled. Events reach Vercel only with `customEvents` on (the team's Pro plan supports them).
